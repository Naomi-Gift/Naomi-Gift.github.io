About

My current priority is privacy: helping Bitcoin nodes run over Tor, I2P and cjdns, and send their own transactions without revealing their IP address.

Selected work
rbitcoin · 2026

Private broadcast that doesn't leak your IP ↗

Sending your own transaction over Tor so no one can link it to you. I closed a leak where the node could dial a clearnet peer directly, made delivery wait for the peer's pong, ended the broadcast once the network echoes the transaction back, and added retries up to Core's limit of 1,000.

Review and iteration: on #1343, each of 3 review rounds found a new way the node could still give itself away. The maintainer finished it and merged it as #1404.

Takeaway: read Bitcoin Core's code first, and for every change ask whether a spy could tell my node apart from a normal one.

rbitcoin · 2026

Onion and I2P services that survive restarts ↗

When Tor or i2pd restarted, the node's hidden addresses died until a manual restart. Now the node notices, stops announcing the dead address, reconnects with Core's backoff and restores every service. Tested against real Tor, real i2pd and Bitcoin Core 29.

Review and iteration: each PR took 4 rounds. Part of that was my tests waiting 1 to 2.6 seconds on the real clock, which made them slow and flaky.

Takeaway: fake the clock in tests, and check exact numbers instead of "it happened eventually".

Bitcoin Core · 2026

Tests that kill surviving mutants in coin selection ↗

A mutant is a small bug put in on purpose. If every test still passes, that line is unguarded. I wrote tests for four of them, including one where the wallet would add a fee discount instead of subtracting it and overpay.

Review and iteration: a maintainer asked me to fold my second PR into this one and to show the diff of each mutant. I did both, and two reviewers then confirmed every mutant was killed.

Takeaway: make a PR easy to check. Show the exact bug the test catches, and keep related work in one place.

BDK · 2026

A wallet that checks the signatures it finalizes ↗

BDK skipped signing an input that already had a signature, without checking it, so a PSBT could finalize with an invalid one. The wallet now always writes a fresh, verified signature for ECDSA and both Taproot paths.

Review and iteration: a reviewer tested it and gave a tested ACK, and asked me to sign my commits.

Takeaway: wallet bugs often hide in shortcuts. Trusting data the wallet didn't make itself is one of them.

A first gossip sync that finishes ↗

A fresh Lightning node could stop syncing early and never learn the network's channels. I checked the three reported causes against master. All three held, and one PR fixes them.

RPC answers that match Bitcoin Core ↗

Reflection and what's next

What I learnt

  • Read the reference first. Most of my review rounds in rbitcoin came from cases Bitcoin Core already handles. Now I read Core's code before I write mine.
  • A test only counts if it fails without the fix. I check this in my own PRs and in every review I do.
  • Privacy leaks hide in behaviour. A node can give itself away by what it sends, when it sends it, and what it never says.
  • Small PRs move faster. One clear change with one clear test gets reviewed. A big one gets questions.
